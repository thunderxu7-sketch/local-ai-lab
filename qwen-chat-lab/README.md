# Qwen Lab：前端转 AI 的第一个本地应用

Next.js + React + TypeScript，通过本地 Ollama 调用 `qwen3:14b`。已实现多轮对话、流式输出、计算器工具调用、本地向量 RAG 和最小 Agent。Agent 可以在同一任务内连续检索资料、调用计算器，再给出带来源的回答。向量模型为 `qwen3-embedding:0.6b`，回答模型为 `qwen3:14b`，均通过本机 Ollama 运行。

## 1. 启动

先确认 Ollama 可用：

```bash
ollama list
```

如果提示无法连接，在另一个终端运行 `ollama serve` 并保持它运行。本机已安装 `qwen3:14b` 和 `qwen3-embedding:0.6b`。在另一台机器重建环境时，还需运行 `ollama pull qwen3-embedding:0.6b`（约 639 MB）。向量模型只用于检索，不会出现在聊天模型选择列表。

启动网页：

```bash
cd qwen-chat-lab
npm run dev
```

打开 <http://127.0.0.1:3010>。服务仅监听本机地址。首次加载 14B 模型通常比后续请求慢；等待界面显示回答即可。

已经安装好的依赖保存在 `node_modules`，版本锁定在 `package-lock.json`。以后重建环境可运行 `npm ci`。需要 Node.js 22；本机使用 22.23.2。

如果端口已占用，先使用已打开的页面，不要重复启动同一个服务。手动停止该终端中的开发服务可按 Ctrl+C。

## 2. 先体验知识库问答

1. 打开左侧“知识库”，展开三份“青竹笔记”示例资料。这是虚构的演示产品，规则仅用于 RAG 练习。
2. 点击“试试语义检索”，发送：**我把一篇笔记误删了，过十天再找还能救回来吗？** 应找到“回收站”原文：删除后保留 14 天，期间可以恢复。
3. 页面先显示检索到的原文，再显示模型回答。也可以问“青竹笔记导入支持哪些格式？单个文件最大多大？”，核对 `.md` / `.txt`、单文件最大 **12 MB**。
4. 点击回答中的 `[1]` 等编号，会展开对应原文，显示文件名、标题和行号。运行记录与 JSON 导出也保存了当时使用的片段。
5. 再问“青竹笔记企业版价格是多少？”：即使命中了产品名称，资料中没有价格，模型也应明确说明信息不足。若没有片段达到相似度门槛，服务端直接提示缺少相关资料，不调用聊天模型。

聊天输入框上方可切换“普通对话”“知识库问答”和“Agent 模式”。普通对话支持多轮上下文和计算器；知识库问答每次只用**当前问题**重新检索，追问请带上主题，例如“青竹笔记恢复联网后如何同步？”三种模式的历史显示在同一页面，但 RAG 和 Agent 的回答不会作为普通聊天的历史输入。

### 放入自己的文档

将 UTF-8 编码的 `.md` 文件放入项目的 `knowledge/` 文件夹，建议用 `#`、`##` 区分主题。每次提问都会重新读取文件并校验本地索引；新增或变化的片段会生成向量，未变化的向量直接复用，删除的片段不再参与检索。编辑后无需重启。知识库页面可以“刷新文档”查看状态，也可以提前点击“更新向量索引”。原有示例可以移走，再放入自己的资料。

当前只读取该目录下的普通 Markdown 文件，不递归读取子目录或符号链接。最多 40 份文档，单文件 128 KB，总计 1 MB，最多 3000 个片段；超出限制会显示错误，不会悄悄截断。

### RAG 的实际流程

```text
knowledge/*.md → 按标题分段 → 每段最多 650 字符，长段重叠 100 字符
文档片段 → 本机 qwen3-embedding:0.6b → 1024 维单位向量 → .local/vector-index.json
用户问题 + 检索指令 → 同一个 Embedding 模型 → 余弦相似度排序
过滤相似度低于 0.45 的片段 → 最多取前 3 段
问题 + 原文 + 引用规则 → 本地 Qwen → 流式回答 + [1] 引用
```

使用本地 Embedding 和精确余弦检索，索引存在 `.local/vector-index.json`，没有外部向量数据库或云 API。小规模知识库直接遍历向量即可。查询遵循 Qwen 的 `Instruct: ...\nQuery:...` 格式，文档输入不加查询指令；文档与问题使用相同模型及维度，并做 L2 归一化。Ollama 的 `truncate: false` 可避免内容被静默截断。

相似度门槛 **0.45** 是本示例的初始设置，不是通用正确率标准。可以在 `lib/knowledge.ts` 调整 `MIN_VECTOR_SIMILARITY`，应先用自己的问题评估漏检与误检。缺少主题的模糊提问仍可能漏检；语义相近的段落也可能缺少所问事实。检索后提示词仍要求模型只依据原文回答，资料不足时明确说明。引用编号只证明可以定位片段，不能自动证明回答受到该片段支持。

索引包含模型 digest、1024 维配置、输入格式版本、文档指纹和片段内容哈希。模型更换、内容变化或缓存损坏后会重建需要的向量；完整构建成功后原子替换文件，失败不会覆盖上一次完整索引。错误会直接显示，不会悄悄退回关键词检索。Embedding 请求跟随取消与超时，最多每批 8 个片段；首次处理较多文档可能较慢。删除全部文档后不会检索旧向量，点击更新索引可将磁盘索引同步为空。

知识库模式的问题最多 2000 字符，最多注入 3 × 650 字符的原文，避免把所有文档塞进 8K 上下文。历史记录保存引用片段快照；之后编辑文档不会改变旧记录。服务端接口 `GET /api/knowledge` 返回文档和索引状态；`POST /api/knowledge` 更新索引，传入 `{ "force": true }` 可强制重建；`POST /api/chat` 请求增加 `"rag": true`，NDJSON 会先发送 `retrieval` 事件。

关键词版首次实测：浏览器中 Qwen 回答导入格式与 12 MB 限制并标注 `[1]`，点击引用成功展开原文；询问未收录的企业版价格时返回“当前知识库未提供这项信息”。零命中请求直接返回缺少资料提示，生成 token 数为 0。运行记录中的回答与来源快照已核对。TypeScript、生产构建和原有 4 项回归检查通过。

向量版实测：浏览器提问“我把一篇笔记误删了，过十天再找还能救回来吗？”，首条来源为“回收站”，余弦相似度约 0.766，Qwen 依据原文回答保留 14 天并标注 `[1]`；点击引用能展开原文。企业版价格问题仍明确说明信息不足，银河系问题低于门槛，未调用聊天模型。当前 11 个片段的索引约 240 KB；更新按钮确认复用 11 个向量、生成 0 个。构建与 6 项回归检查通过；临时隔离目录中的真实 Embedding 检查覆盖首次构建、缓存复用、修改、删除、并发更新、模型 digest 变化、损坏缓存恢复和取消保留旧索引，报告位于 `.local/vector-verification.json`。

## 3. 体验 Agent 连续调用工具

1. 切换到“Agent 模式”，点击“试试查规则并计算”，再发送。
2. 示例问题是：**请先检索青竹笔记的导入规则，再调用计算器：一批文件都达到单文件上限时，总大小是多少？请给出计算式和来源。**
3. 观察工具卡片：先 `search_knowledge` 检索到文件规则，再由模型提取参数，调用 `calculate` 计算 `12 × 8 = 96`。这是依据文件数和单文件限制推算的理论合计，不是文档额外规定的批次总大小限制。
4. 点击回答中的引用编号，会打开本轮来源，展开原文。工具卡片显示参数、结果、轮次和耗时；“运行记录”保存整个任务与当时引用的原文快照。
5. 换成“用计算器计算 27 × 16”，观察是否只调用计算器；再问资料中没有的价格，观察模型是否承认缺少信息。

```text
用户任务 → Qwen 决定下一步 → 返回 tool_calls
                           ↓
                应用校验参数并执行本地工具
                           ↓
              把工具结果加入 messages，再请求 Qwen
                           ↓
                继续调用工具，或输出最终答案
```

与 RAG 的固定“先检索再回答”不同，Agent 把 `search_knowledge` 和 `calculate` 都作为可选工具交给模型。应用执行真实工具调用，不根据用户问题关键词写死调用顺序。每次任务重新开始，不带前一任务的聊天历史；依赖上一步结果的工具应在下一轮调用。

示例明确要求使用计算器，因为实测 `qwen3:14b` 在关闭思考时有时会查到数字后直接口算，系统提示不能保证每次都遵循工具要求。应用会检查最终草稿中的显式数值等式：如果尚无成功的计算器调用，就清除草稿并把核验反馈交给模型，最多补做一次；仍不满足时明确报错。这是有限的等式检查，不是完整的数学解析或答案正确性验证。运行记录的 `agentCorrections` 记录补做次数。

卡片只显示实际发生的调用；回答正确与工具链完整是两件需要分别核对的事。引用编号也只检查是否存在，并不自动验证回答与来源是否一致。

每次最多 3 轮工具执行、4 次工具调用、2 次检索；每次检索最多返回 2 个片段。重复片段沿用本轮引用编号，新片段分配新编号。问题最多 2000 字符，问题与 System Prompt 合计最多 2500 字符，工具上下文超过 9000 字符时明确报错；这些字符限额只是对 8K 上下文的粗略保护。停止按钮会取消后续模型和检索请求。工具错误会反馈给模型，由它说明问题或在限额内重试，不会执行模型生成的任意代码。

接口 `POST /api/chat` 增加 `"agent": true`，不能与 `"rag": true` 同时启用。NDJSON 的 `tool` 事件记录步骤状态，`retrieval` 更新本轮统一来源，`resetResponse` 清除工具调用前或待核验的临时文本，`notice` 显示核验进度，最后 `done` 标记完成。两种工具继续使用现有本地模型与索引，无需新下载模型。

Agent 版实测：浏览器完整执行检索 → 核验补做 → 计算器 → 带来源的 96 MB 回答，点击引用成功展开原文。纯算术 `27 × 16` 仅调用计算器并返回 432；企业版价格问题执行检索后说明资料缺失；在检索开始时取消请求，运行和工具均记录为已停止。11 项回归检查及生产构建通过。记录摘要见 `.local/agent-verification.json`，网页截图见 `.local/agent-tools-ui.png` 与 `.local/agent-ui.png`。

## 4. 继续体验普通对话

### 实验一：看懂流式响应

在首页选择“理解一个概念”，点击发送。观察文字逐渐出现，再点击“停止生成”。停止后可以继续提问。

打开浏览器开发者工具的 Network，找到 `POST /api/chat`。请求中包含：

```json
{
  "model": "qwen3:14b",
  "system": "你是一位耐心、准确的中文技术助手。",
  "think": false,
  "messages": [{ "role": "user", "content": "什么是 Token？" }]
}
```

响应是 NDJSON：每一行是一个 JSON 对象。网络分块不等于 JSON 行，也不一定是完整中文字符；`lib/ndjson.ts` 负责增量 UTF-8 解码与拼接。最后的 `done: true` 表示生成结束。

### 实验二：验证上下文

1. 发送“我的项目叫青竹，请记住。”
2. 再问“我的项目叫什么？”。
3. 点击“新对话”，再次问同一个问题。
4. 在 Network 中比较三次请求中的 `messages`。

历史由应用每次重新发送，模型不会自动跨请求记住用户。取消或失败的轮次不加入下一次请求的上下文。当前对话草稿保存在浏览器 localStorage；“新对话”清空草稿，但保留服务器端实验记录。

### 实验三：做一组对照

点击右上角参数图标，修改 System Prompt，或开启思考模式。用同一个问题测试，查看“运行记录”中的回答、首字耗时、总耗时和生成速度。

比较时保持其他条件一致，最好各自开启新对话。不要把不同上下文的结果当作严格对照。运行完成只代表链路正常，回答正确性需要单独检查。

## 5. 建立第一批评测题

### 项目知识库与 Agent 的效果评测

知识库新增 `10-qwen-lab-start.md`、`11-qwen-lab-knowledge.md`、`12-qwen-lab-agent.md`、`13-qwen-lab-runtime.md`，依据 README 整理并核对对应代码。它们是项目说明的整理版本，不会自动跟随 README 更新；功能修改后应同步维护。原有“青竹笔记”虚构资料保留，可观察检索是否会混淆两个产品。

打开网页左侧“效果评测”，选择轮次，展开问题即可对照预期要点、实际回答、引用原文和工具记录。可切换首次基线与调整后的结果，导出 JSON，或点击“用本轮设置再问一次”把问题、模式及模型参数填入对话页，然后发送。该按钮不会覆盖已有评测结果；新的对话会进入运行记录。

固定题集在 `eval/project-cases.json`：3 道直接问答、3 道改写问法、2 道检索后计算、2 道资料缺失。问题、预期和检查规则在运行前确定。参考答案与评分条件不放入知识库，也不发送给模型。执行完整题集：

```bash
npm run eval:project -- --label 新一轮
```

只复现某几题可用 `npm run eval:project -- --ids P07,P08 --label 局部复现`。脚本按顺序请求本机应用，不并行占用模型；每完成一题便原子保存到 `.local/project-evals/`，可在网页刷新查看进度。Ctrl+C 会中止当前请求并保留已运行结果。`--think` 可开启思考，但会成为新的实验设置，不应与关闭思考的耗时直接混作严格对照。

“规则检查”只验证完成事件、预期段落是否被检索到、关键文本线索、引用编号是否存在、真实工具顺序与计算参数。它不能判定所有语义错误。没有答案的两道题不纳入依据命中率的分母。内容复核需另行对照回答、来源和工具记录；本次复核由编码助手完成，不是独立人工盲评。重新运行的报告默认保持“待复核”，不会沿用旧轮次的通过标记。

每轮报告记录题集、知识库、实现的 SHA-256 指纹和本机模型 digest。保留旧报告与失败回答，不通过修改题目或删掉失败记录来提高通过率。这里只是 10 题的小样本练习，不代表模型总体准确率；首次加载和缓存也会影响耗时。

本次实测：7 份文档、29 个片段，首次基线内容复核通过 9/10；P08 检索与计算正确，但缺少来源编号。仅强化 Agent 在计算后保留原始数据引用的提示，原题全量复跑后为 10/10，8 道有答案题均召回了预期依据，2 道资料缺失题均未编造答案。这是同一调试题集上的改善，不是独立测试集结论。两轮报告均可在网页查看；尚有 P06 网页入口提示不够直接、P07 LaTeX 按纯文本显示等可用性细节。

## 运行边界

- 默认关闭思考，输出最多 512 token，上下文配置为 8192 token，请求超时 180 秒。
- 应用限制单条消息 6000 字符、最多 40 条历史、总内容 16000 字符。字符限制是粗略保护，不等于精确 token 预算；长对话请新开会话。
- 模型列表来自 Ollama；这个页面不直接加载 MLX 权重，也不启动 MLX 训练。
- 不同时进行 MLX 训练和 14B 推理，以便给 24GB 统一内存留出余量。
- 默认开发模式只用于本机学习。应用没有账号、多用户隔离或联网搜索。
